# 修正「多位管理者同時登入時系統卡死／崩潰」

## 目前確認到的狀況（來自程式碼閱讀）

`src/lib/tournament-store.tsx` 的管理者同步是「拉取 → 合併 → 發佈」兩段 effect，兩者共用同一個 `lastPayload` 防迴圈旗標，但兩邊存的內容不一致：

- 拉取端 `apply()` 把 `lastPayload` 設成**雲端傳來的原始快照**。
- 合併後的本機狀態（`mergePlayers` 會重新編號 seed、`mergeMatches` 會保留本機較新的對戰）通常**和原始快照不同**。
- 於是發佈端 effect 比對後認為「本機有變動」→ 立刻發佈；另一台管理者收到後同樣合併出不同結果 → 再發佈回來。

兩台以上管理者同時上線時，這會變成每 250ms 一次的互相發佈迴圈：Realtime 事件與寫入不斷累積，畫面持續重繪而卡死。另外兩個放大因素：

- Realtime 訂閱不限 tournament，任何一列 `tournaments` 變動都會觸發完整 `pull()`。
- 決賽結束後的封存 effect 是每台裝置各自執行，多位管理者會同時呼叫 `finishTournament`。

診斷依據為程式碼結構，尚未實機重現，因此第一步是先重現確認。

## 修正步驟

1. **重現**：以兩個瀏覽器工作階段同時以管理者身分登入同一場賽事，觀察發佈次數與 Realtime 事件是否無上限增長。
2. **統一防迴圈基準**：`apply()` 改為在合併完成後，用「合併後的本機狀態」寫入 `lastPayload`，讓發佈端不會把合併結果誤判為新的本機編輯。
3. **加入回音抑制**：剛套用雲端快照後的短時間內（約一個發佈週期）不主動發佈，除了真的有本機操作（新增選手、計分、產生賽程）才發佈。
4. **收斂 Realtime 觸發**：管理者的訂閱加上目前追蹤賽事的 filter，避免其他賽事的變動造成整體重新拉取；同時對連續事件做合併節流。
5. **封存只做一次**：自動封存改為由發佈端唯一路徑處理，並容忍「已封存」的回應，避免多位管理者重複寫入。
6. **驗證**：兩台管理者同時新增選手、同時計分、強制結束賽事，確認狀態一致、發佈次數有限、畫面不再卡死。

## 技術細節

- `src/lib/tournament-store.tsx`：`apply()` 內以合併結果重算 `lastPayload`；新增 `lastApplyAt` ref 做回音抑制；Realtime `postgres_changes` 加上 `filter: id=eq.<followedId>`；封存 effect 加入已封存的容錯。
- `src/lib/live-merge.ts`：不改變合併語意，必要時只在 seed 無變化時回傳原物件以減少重繪。
- 不需資料庫變更。
